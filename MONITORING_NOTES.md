# Monitoring Notes (Week 12)

## Part A: Predictions (made before any data)

1. **Slowest endpoint:** Authentication (login). Password hashing takes time to check.
2. **Most errors:** Login. Users enter a wrong password or wrong email.

## Part E: What the data shows

Traffic was generated with `traffic.js` against my local server: one run of
60 requests and one run of 200 (plus one lookup request per run), so
`/api/stats` counted 262 requests in total.

| Measure | Value |
|---|---|
| Total requests | 262 |
| Client errors (4xx) | 158 (60.3%) |
| Server errors (5xx) | 0 |
| Error rate (5xx only) | 0% |
| Average response time | 1.5 ms |

| Route | Count | 4xx | Avg ms | Max ms |
|---|---|---|---|---|
| GET /api/artisans/ | 51 | 0 | 3.7 | 55.6 |
| GET /api/artisans/:id | 57 | 30 | 1.7 | 2.5 |
| GET /api/health | 26 | 0 | 0.6 | 0.9 |
| GET (no route) | 128 | 128 | 0.8 | 1.2 |

### 1. Predictions vs data

- **Slowest endpoint:** I predicted login. My traffic mix never called
  login, so this prediction is **untested**, not wrong. Among the routes I
  did test, the slowest on average was `GET /api/artisans/` at 3.7 ms,
  because it queries the database for a list. The fastest was
  `GET /api/health` at 0.6 ms, which does no database work.
- **Most errors:** I predicted login. Again, login was not in my traffic.
  Among the routes I tested, `(no route)` had the most 4xx responses (128),
  and `GET /api/artisans/:id` had 30 of its 57 calls end in 404.

### 2. A real pattern in my traffic

`GET /api/artisans/` averaged 3.7 ms, but its slowest call was 55.6 ms,
about 15 times the average. The log shows that 55.6 ms request was the
very first request after the server started. Every other call to that
route was a few milliseconds. In the same traffic, 30 of the 57 calls to
`GET /api/artisans/:id` (53%) returned 404, because the script
deliberately asks for an id that does not exist.

The `(no route)` row (128 requests) mixes several things. It matches the
traffic script's mix: 66 requests with a missing or wrong key (401),
23 with the wrong key scope (403), 13 rate-limit rejections (429), and the
remaining 26 calls to a path that does not exist (404).

There were no 5xx errors at all, so the error rate is 0%. The high 4xx
count (60.3%) is not a sign of a broken API. It comes from the script's
deliberate mix of bad requests. The 401s all had `caller: "none"`, and they
came from my own script, not from probing by outsiders.

### 3. Why I think this happens, and what I would check next

The first request is slow because it pays one-time start-up costs, most
likely opening a database connection and running the first query. I would
check this by restarting the server and sending the same request 20 times,
to see whether only the first one is slow. If the slow spike moves to a
different request, the cause is something else, such as the database.

I would also test login on purpose. My prediction was that password
hashing makes it the slowest endpoint, and I have not tested that yet.

### 4. One alert for production

Alert when `errorRatePercent` (5xx only) is above 2% for 5 minutes.
When it fires, a person should be paged to find the cause. While they work
on it, the app should keep serving users with a fallback (saved data or a
clear message) instead of failing, as in Week 11.

### Limits of this data

The counters live in server memory, so they reset on restart. The traffic
was generated by my own script against a local server, so the proportions
of errors reflect the script's mix, not real users.
